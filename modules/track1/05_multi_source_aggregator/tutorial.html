00Before You Start

Finished Module 3 and Module 4 — this module imports Module 4's PubMed connector directly and reuses it unchanged.

01The Big Analogy

Two rivers, one tracer dye Two rivers join at a confluence and become one wider river — from that point on, you can't tell by looking which water came from which tributary. Except hydrologists actually can, because they release a harmless tracer dye upstream, a different color in each river, before the joining point. Any sample taken downstream, no matter how mixed, still tests positive for exactly one dye — proving which tributary that water originated from, even after merging.

source_format — set once, back in Module 3 and Module 4's parsers, long before this module exists — is that dye. Merging never erases it.

02What Happens, Step by Step

  1. search_pubmed() — literally Module 4's search_and_fetch(), imported and called unchanged — returns real PubMed Records
  2. fetch_arxiv() sends a real boolean query to arXiv's Atom API and returns real arXiv Records
  3. parse_arxiv_feed() walks the Atom XML's namespaced <entry> elements, extracting title/authors/year/venue/abstract/DOI into the same Record shape Module 3 defined
  4. merge_sources() concatenates any number of source lists into one corpus
  5. It also tallies a CorpusStats count per source_format — proof, not assertion, that every record's origin is still traceable after merging

04The Code, Explained

The merge itself is deliberately almost nothing — the interesting work already happened upstream, in each source's parser:

def merge_sources(*source_lists: list[Record]) -> tuple[list[Record], CorpusStats]:
    merged: list[Record] = []
    for records in source_lists:
        merged.extend(records)

    counts: dict[str, int] = {}
    for r in merged:
        counts[r.source_format] = counts.get(r.source_format, 0) + 1

    return merged, CorpusStats(counts_by_source=counts, total=len(merged))

That's the whole proof mechanism: counts isn't hand-typed or assumed, it's computed by actually walking the merged list and reading each record's source_format back out. If merging silently corrupted provenance, this count would be wrong — and the self-checks would catch it.

05Limits / What You Cannot Do Yet

Can't do yet

  • Remove duplicate records that both sources happen to return — a paper indexed in both PubMed and arXiv (as a preprint) shows up twice right now
  • Handle a source's rate limits or pagination beyond the first page of results
  • Clean up messy real metadata (arXiv's author list quirks are kept as-is — see DECISIONS.md)

Can do

  • Pull real results from two structurally different live APIs into one list
  • Prove, by computation rather than assertion, that provenance survives merging
  • Accept any number of sources through the same function, unmodified

07Brain Exercise

The Limits section admits a paper indexed in both PubMed and arXiv would appear twice in the merged corpus right now. Why doesn't this module just deduplicate before returning the corpus?
Because deduplication needs its own real logic — deciding whether two differently-titled, differently-formatted records actually describe the same paper is genuinely hard (exact DOI match is easy; fuzzy title/author matching across a preprint and its later published version is not). Folding that into "the module that merges lists" would hide a substantial algorithm inside a function that's supposed to be almost nothing. Module 6 exists specifically so deduplication gets its own space to be explained properly, rather than becoming a rushed afterthought bolted onto this one.

08There Are No Dumb Questions

Why does merge_sources() take *source_lists instead of just two fixed parameters, pubmed_records and arxiv_records?
Because nothing about the merge logic is specific to those two sources — it's just concatenation plus a count. A fixed two-parameter signature would need editing every time a third source (Module 21's scoping-review variant, for instance) wants to reuse it. The variadic signature means it never needs to change.
The arXiv author list example had "Ph. D." and " PEng" as separate authors — shouldn't the parser filter those out?
It's tempting, but filtering requires a rule ("things that look like credentials aren't names") that will inevitably misfire on some real name somewhere. This module's job is faithful normalization of structure (get the right fields into the right places), not judgment calls about content quality — that boundary is deliberate, not an oversight.
Could I add a third source, like Crossref, right now?
Yes — write a fetch_crossref(...) -> list[Record] function using Module 3's existing parse_crossref_json(), and pass its result as a third argument to merge_sources(). Nothing else in this module needs to change.

09What's Next

The corpus is real, merged, and provenance-tagged — and, as this module's Brain Exercise admits, almost certainly contains duplicates. Module 6 builds the actual deduplication engine: exact DOI matching first, then fuzzy title/author matching for the harder cases.
