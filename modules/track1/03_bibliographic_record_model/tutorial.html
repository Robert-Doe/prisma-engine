01The Big Analogy

Three delegates, one shared notepad Three witnesses describe the same event to a UN committee — one in French, one in Mandarin, one in Arabic. Each account is complete and correct in its own language, but nobody on the committee can compare them side by side until a translator converts all three into one shared working language. The translator doesn't change what was said — they change the shape it's expressed in, so it becomes comparable.

parse_ris(), parse_bibtex(), and parse_crossref_json() are three translators. Each reads a different "language" (RIS's tag-per-line, BibTeX's braced fields, Crossref's nested JSON), and all three write into the same shared notepad: the Record dataclass.

02What Happens, Step by Step

  1. A parser receives raw text (RIS/BibTeX) or a dict (Crossref-shaped JSON) describing one paper
  2. It extracts that format's fields using that format's own rules — RIS's TAG - value lines, BibTeX's key = {value} pairs, Crossref's nested title/author/published structure
  3. Format-specific quirks get resolved during extraction — multiple RIS AU lines become a list, BibTeX's "A and B" author string gets split on " and ", Crossref's JATS-XML-wrapped abstract gets its tags stripped
  4. The extracted values are packed into a Record — the same seven fields, regardless of which parser produced it
  5. If the input is missing a title (the one field nothing downstream can work without), the parser raises ParseError instead of returning a half-built record

04The Code, Explained

Notice all three parsers share an identical shape even though their parsing logic is completely different — extract fields in the source format's own terms, then construct one Record:

def parse_crossref_json(data: dict) -> Record:
    titles = data.get("title") or []
    if not titles:
        raise ParseError("Crossref-shaped record has no title")
    # ... extract authors, year, venue, abstract in Crossref's terms ...
    return Record(title=titles[0], authors=authors, year=year,
                   venue=..., abstract=..., doi=data.get("DOI"),
                   source_format="CrossrefJSON")

The abstract-cleaning step is worth a close look, because it's a real, documented quirk of a real API, not a hypothetical edge case:

abstract = data.get("abstract")
if abstract:
    # Crossref abstracts are frequently wrapped in JATS XML tags
    abstract = re.sub(r"<[^>]+>", "", abstract).strip()

05Limits / What You Cannot Do Yet

Can't do yet

  • Parse arbitrary, deeply-nested BibTeX (only flat, brace-delimited fields — see DECISIONS.md)
  • Tell two Records apart as duplicates or not — that's Module 6
  • Fetch anything from a live source — every input here is a literal string or dict

Can do

  • Take the same paper in three real, independently-specified formats and prove they converge on one shape
  • Handle a documented real-world quirk (JATS-wrapped Crossref abstracts) correctly, not just the easy case
  • Fail loudly, not silently, when a record has no title

Getting None for a field that should be filled? Check the exact field name your input uses — RIS field tags are case-sensitive two-letter codes (PY, not Py or YEAR), and BibTeX field keys are matched case-insensitively but still need to exactly match what the parser looks up (journal, not publication).

07Brain Exercise

Why does ParseError require only a title, when a Record with no DOI and no abstract is arguably almost as useless downstream?
Because "almost as useless" isn't the same as "structurally broken." A record missing a DOI or abstract is real and common — plenty of legitimate preprints and older papers lack one or both — and later modules (screening, extraction) can still meaningfully operate on a title-and-authors-only record, even if imperfectly. A record with no title isn't degraded, it's meaningless: there's nothing to screen, display, or deduplicate against. The line is drawn at "unusable," not "imperfect."

08There Are No Dumb Questions

Why keep source_format at all if every Record ends up looking the same afterward?
They look the same in the fields that matter for search/screening — but if Module 6's deduplication engine ever produces a surprising merge, knowing "this one came from Crossref, that one came from a hand-exported RIS file" is often the fastest way to figure out why.
What happens if a BibTeX entry has a nested brace, like title = {The {Real} Cost of Remote Work}?
The regex-based parser here would stop at the first closing brace, truncating the title. This is the documented scope limit from DECISIONS.md, not a silent failure — a production-grade BibTeX parser would need a real recursive parser, which is a reasonable, deliberate line to not cross for this module.
Is the Crossref JSON shape in this module guaranteed to match what Module 4 actually gets back from the live API?
It's built to match Crossref's documented public schema, but "documented" and "what a live call returns today" can drift. Module 4 is where that gets checked against reality — if it doesn't match, that's real, useful information Module 4's tutorial will surface, not swept under the rug.
