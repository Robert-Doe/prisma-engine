Module 14 — Track 1: Core EngineEvidence Table Builder

00Before You Start

Finished Module 10 — this module assembles many of that module's ExtractedRecords into one table.

01The Big Analogy

A stack of index cards vs. a spreadsheet Three studies extracted onto three separate index cards can each be read individually — but to answer "how many studies found a positive effect," you'd have to hold all three cards, read each one, and count by hand. Transcribe the same three cards into one spreadsheet and the answer is a single glance down one column.

Nothing about the underlying facts changes between the index cards and the spreadsheet. What changes is what you can do with them. build_evidence_table() is the transcription step — and table.to_dict_rows()'s column-reading in this module's demo is the glance down the column that the index cards alone could never give you directly.

02What Happens, Step by Step

  1. Each study has already been through Module 10's extract(), producing an ExtractedRecord
  2. build_evidence_table() re-validates every row against the table's target schema — not trusting that validation already happened correctly upstream
  3. A row that fails re-validation raises SchemaMismatchError, naming which study and why, before it ever joins the table
  4. EvidenceTable.column_names() fixes the column order: title, year, then every schema field in declaration order
  5. render_markdown() produces a real, readable table; to_dict_rows() produces the same data ready for column-wise analysis

04The Code, Explained

The re-validation step that's the actual point of this module:

def build_evidence_table(extracted_records, schema):
    for er in extracted_records:
        try:
            validate_extraction(schema, er.data)
        except ExtractionValidationError as e:
            raise SchemaMismatchError(
                f'"{er.record.title}" does not satisfy the target schema: {e}'
            ) from e
    return EvidenceTable(schema=schema, rows=list(extracted_records))

And the column-pull that's the whole reason a table beats a stack of cards:

directions = [row["effect_direction"] for row in table.to_dict_rows()]
# ['positive', 'no effect', 'mixed']

05Limits / What You Cannot Do Yet

Can't do yet

  • Mix rows extracted under genuinely different schemas in one table — the table assumes exactly one shared schema throughout
  • Do anything statistical with the assembled columns — that's Modules 16-17
  • Handle a schema change mid-review (if the extraction form gets revised, old rows need re-extraction, not silent tolerance)

Can do

  • Turn many individually-valid extractions into one genuinely comparable table
  • Catch a row that shouldn't be in the table, even if it individually looked fine when it was created
  • Support both a human-readable rendering and a machine-usable row format from the same underlying data

07Brain Exercise

Module 10's `extract()` already validates data before returning an `ExtractedRecord`. Why does this module bother re-validating the exact same data?
Because `ExtractedRecord` is a plain, ordinary dataclass — nothing stops a caller from constructing one directly with ExtractedRecord(record=..., data={...}), completely bypassing extract() and the validation inside it. This module's own demo does exactly that on purpose, to build the "bad" row it then catches. Trusting that every ExtractedRecord that reaches this module must have gone through validated extract() would be trusting a convention, not a guarantee — and this module's whole job is guaranteeing the table it produces is actually comparable, not just usually comparable.

08There Are No Dumb Questions

What happens to a study whose optional `outcome_measure` field was never filled in?
It renders as a blank cell in the markdown table and is simply absent from that row's dict in `to_dict_rows()`. Nothing errors — Module 10 already marked that field optional, and this module respects that, rather than treating "missing optional data" the same as "missing required data."
Could I build two different evidence tables from the same corpus, using two different schemas?
Yes — `build_evidence_table()` takes the schema as an explicit argument every time, so nothing ties a corpus to one fixed schema. You could, for instance, extract the same studies once against a quantitative-outcomes schema and once against a study-quality schema, producing two separate, separately-comparable tables.
Why does the error message name the study's title instead of, say, a row index?
Because "row 2 failed validation" forces a human to go count rows to figure out which study that even was. Naming the title directly means the error is immediately actionable — you know exactly which extraction to go fix without any extra lookup.
