00Before You Start

You need Prerequisites 2 and 3, plus finished Module 2 and Module 3 — this module sends Module 2's query string to a real API and parses the reply with Module 3's Record model.

01The Big Analogy

Mailing the letter Every module up to now has been drafting a letter — carefully worded, logically structured, addressed as precisely as we know how. This module is the moment it actually gets mailed to a real foreign postal system, and a reply comes back.

Two things happen the moment a letter actually goes out that never happen while you're still drafting it. First, you discover the address format the recipient's postal system actually uses isn't quite what you assumed — our MeSH:"Telework" label needs translating into PubMed's own "Telework"[mesh] dialect before their system can read it at all. Second — and this is the part that can't happen with a draft sitting on your desk — you find out one of the facts in your letter was simply wrong. We wrote "Telework" assuming it was a real, standard heading. PubMed's reply says: no such heading exists. Only mailing the letter could have told us that.

02What Happens, Step by Step

  1. verify_mesh_term() checks a controlled-vocabulary term against the live database before trusting it — run on both "Telework" and "Teleworking," only the second is real
  2. translate_vocab_tag() rewrites Module 2's internal MeSH:"X" convention into PubMed's real "X"[mesh] field-tag syntax
  3. esearch() sends the translated query to PubMed, getting back matching PMIDs, a total count, and PubMed's own parsed interpretation of the query
  4. After a courtesy delay, esummary() fetches metadata for those PMIDs in one batched call
  5. parse_pubmed_summary() converts each raw summary into a Module 3 Record — extracting year from a free-text pubdate string, finding the DOI inside a list of article-ID objects, and stripping PubMed's cosmetic trailing period from titles

04The Code, Explained

The translation function exists purely because of what a real call revealed — this is the module's central lesson made concrete in code:

def translate_vocab_tag(query, our_tag="MeSH", pubmed_tag="mesh"):
    """Sent literally, MeSH:"Telework" does NOT restrict the search —
    PubMed treats "MeSH:" as its own free-text phrase. Verified, not assumed."""
    pattern = re.compile(rf'{re.escape(our_tag)}:"([^"]+)"')
    return pattern.sub(lambda m: f'"{m.group(1)}"[{pubmed_tag}]', query)

And the verification step that caught the actual error:

def verify_mesh_term(term):
    resp = requests.get(ESEARCH_URL, params={
        "db": "pubmed", "term": f'"{term}"[mesh]', "retmode": "json"
    }, headers={"User-Agent": USER_AGENT}, timeout=15)
    result = resp.json()["esearchresult"]
    not_found = result.get("warninglist", {}).get("quotedphrasesnotfound", [])
    return int(result.get("count", 0)) > 0 and not not_found

05Limits / What You Cannot Do Yet

Can't do yet

  • Fetch abstracts — esummary doesn't include them; that needs efetch's XML format, out of scope here
  • Query any source besides PubMed — Crossref was tested and rejected for this specific job (see DECISIONS.md), not wired up as an alternative
  • Combine results from multiple sources into one corpus — that's Module 5
  • Reproduce the exact same output twice — live data changes

Can do

  • Prove a boolean query built entirely offline is honored as real boolean logic by a real, live system
  • Catch a wrong assumption (an invalid MeSH term) by actually checking, not by re-reading the assumption more carefully
  • Turn a live API's raw reply into the exact same Record shape every other source uses

Getting a connection error or timeout? This module needs outbound internet access on port 443. If you're behind a restrictive firewall/proxy, requests.get(...) will raise a ConnectionError — that's expected in that environment, not a bug in the code. Getting a 429 or rate-limit error? You're calling faster than NCBI's unauthenticated limit (3 req/sec) — the built-in courtesy delay should prevent this in normal use; if you're running the module in a tight loop for experimentation, add a longer delay.

07Brain Exercise

Module 2 and Module 3's DECISIONS.md both explicitly flagged "Telework" as "illustrative, not verified" rather than just using it confidently. Why did that hedge matter, concretely?
Because it turned out to be wrong, and the hedge is exactly what kept that wrongness from being presented as fact anywhere in the course before now. If Modules 2-3 had asserted "Telework" was a real MeSH heading, this module's discovery that it isn't would be a correction to earlier material — a crack in the course's own claimed rigor. Because they said "not verified" instead, the exact same discovery is simply the payoff of a claim those modules never made. Precise hedging isn't caution for its own sake — it's what makes it possible to be wrong about a detail without being wrong about what you said.

08There Are No Dumb Questions

Why not just use Crossref, since Module 3 already models its exact JSON shape?
Because Crossref doesn't actually search on our boolean query — it does relevance-ranked keyword search and ignores the AND/OR/quote structure. Using it here would make this module's core claim (a boolean query gets honored by a live system) false while looking like it succeeded. Module 3's Crossref parser isn't wasted, though — it's exactly what you'd use if you were pulling metadata for a single already-known DOI from Crossref, a genuinely common task.
Couldn't verify_mesh_term() have just been run once, offline, and the correct term hardcoded from the start?
That's exactly what should happen in a real review's workflow — you verify controlled-vocabulary terms once, early, against the live database, then use the confirmed term from then on. This module builds that verification step as reusable code specifically so it's not a one-off manual lookup a reviewer does and forgets, but a checkable, repeatable part of the pipeline.
Is it a problem that this module's output isn't reproducible?
Not a defect — a real property of live data that every subsequent module has to handle honestly. Real systematic reviews record the exact date a search was run for exactly this reason: "905 results" is only meaningful alongside "as of 2026-07-27." Module 7's PRISMA Flow Tracker will formalize logging this kind of provenance.
