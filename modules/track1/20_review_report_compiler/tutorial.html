00Before You Start

This module imports and calls real functions from fourteen prior modules. If any of Modules 1, 2, 3, 5, 6, 7, 8, 10, 12, 14, 16, 17, 18, or 19 feels unfamiliar, this is the module that will make that gap obvious — go back and finish it first.

01The Big Analogy

Expediting In a real restaurant kitchen, a dozen different stations each independently prepare one component — the grill station sears the protein, the sauté station makes the sauce, the garde manger plates the garnish. None of them alone is dinner. The expediter is the person standing at the pass who takes every finished component and plates them together onto one plate, in the right arrangement, and sends out one finished dish.

compile_report() is the expediter. It doesn't cook anything itself — every real ingredient (the research question, the live search results, the PRISMA diagram, the evidence table, the forest and funnel plots) was already prepared by a station that came before it. This module's entire job is arranging them, correctly, onto one plate.

02What Happens, Step by Step

  1. Formalize + search (Modules 1-2): build the research question and boolean query
  2. Search, aggregate, dedup, track, screen (Modules 4-8), for real, live: PubMed + arXiv results merged, deduplicated, logged into a PrismaFlowTracker, screened
  3. Render the PRISMA diagram (Module 12) from that tracker's real state
  4. Extract and table (Modules 10, 14): this course's established illustrative studies, extracted and assembled into an evidence table
  5. Pool and plot (Modules 16-18): compute effect sizes, pool them (random-effects), render a forest plot
  6. Check for bias (Module 19): Egger's test and a funnel plot on the same pooled studies
  7. Assemble: every result above gets escaped and interpolated into one HTML document, saved alongside its three image assets

05Limits / What You Cannot Do Yet

Can't do yet

  • Screen the live-fetched records all the way through to real quantitative synthesis — the live and illustrative halves are thematically aligned, not the same records
  • Export to PDF or Word — HTML only (a browser's own "print to PDF" gets you the rest of the way)
  • Regenerate incrementally — every run recompiles everything from scratch, including fresh live network calls

Can do

  • Produce one real, complete, openable report from a single function call
  • Prove every section is backed by a real, checkable artifact — not just prose describing what a report would contain
  • Generate a narrative conclusion that honestly reflects its own numbers, hedged exactly as much as the data warrants

07Brain Exercise

The report's narrative synthesis (Section 7) counts "the 4 records that passed title/abstract screening in the live search" in the same sentence as the illustrative meta-analysis numbers. Is that a contradiction?
It's a boundary the report is honest about, not a hidden contradiction. Read closely, the sentence describes two different things happening to be discussed together: the live search found 4 real records passing screening, and separately, a set of illustrative studies was synthesized to demonstrate the statistical machinery. Nothing in the report claims those 4 real records are the same studies that got pooled into the odds ratio — because they aren't. This is the same honesty principle from Module 9 and Module 16 carried all the way to the final report: say what's real and what's illustrative, don't blur the two together for a tidier-looking conclusion.

08There Are No Dumb Questions

Why compile a report at all, instead of just running each module separately and reading their outputs one at a time?
Because a real review's audience — a journal, a policy team, a supervisor — doesn't want fourteen separate terminal outputs. Part of this module's own proof is that a pipeline built as many small, independently-verifiable pieces can still converge into one coherent, standalone artifact, which is exactly the causal claim this module set out to demonstrate.
What happens if one of the fourteen imported modules has been modified since this module was built?
This module has no independent copy of any prior module's logic — it imports and calls the real, current functions every time it runs. If Module 8's screening rules changed, this module's report would reflect that change automatically the next time it's run, for better or worse. That's a real, direct consequence of reuse rather than duplication, the same principle every module since Module 4 has followed.
Could this module be adapted for one of Track 2's review types instead of a PRISMA-style systematic review?
Structurally, yes — swap which modules' outputs get compiled (a scoping review's charting form instead of a meta-analysis, for instance), and the "gather real artifacts, assemble one document" pattern still applies. That's genuinely close to what several Track 2 modules do next.
