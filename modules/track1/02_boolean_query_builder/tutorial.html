Prerequisites: Boolean Search & Controlled Vocabulary

00Before You Start

You need Prerequisite 2 (AND/OR/NOT, controlled vocabulary) and the finished Module 1 — this module consumes the exact ResearchQuestion object Module 1 produces.

01The Big Analogy

Casting nets, not one line at a time Fishing with a single hook for "remote work" catches only papers using that exact phrase. Cast a net instead — one net per concept, woven from every synonym you can think of ("remote work" OR "telecommut*" OR "work from home") — and anything matching any strand gets caught. That net is one OR-group.

Now put two nets in the boat's path, one after the other: a fish only ends up in your hold if it passed through both the population net and the intervention net. That's AND joining two OR-groups.

And here's the part that surprises people: this module deliberately doesn't cast a net for "productivity" or "in-office work" at all. Not because those concepts don't matter — because casting a net that early risks losing fish that are exactly what you want but never said the word "productivity" in the water where your net can see it (the title or abstract). Those two nets get cast later, at the dock, once you can actually pick up each catch and look closely — that's screening (Module 8), not searching.

02What Happens, Step by Step

  1. You give build_query() a validated ResearchQuestion plus a dict of SlotTerms — free-text synonyms and optional controlled-vocabulary terms, per slot
  2. If you don't specify which slots participate, it defaults to DEFAULT_SEARCH_SLOTS[framework] — population + intervention for PICO, deliberately excluding comparison and outcome
  3. For each participating slot, build_or_group() quotes any multi-word term, tags controlled-vocabulary terms with MeSH: (or whatever vocabulary tag you specify), and joins everything inside that slot with OR
  4. The finished OR-groups are joined with AND into one search string
  5. If a participating slot has no SlotTerms at all, or a SlotTerms with nothing in it, construction stops with a named error instead of producing a broken query

04The Code, Explained

The whole compilation step, in full:

def build_query(rq, terms, search_slots=None):
    search_slots = search_slots or DEFAULT_SEARCH_SLOTS[rq.framework]
    groups = []
    for slot in search_slots:
        if slot not in terms:
            raise MissingTermsError(slot)
        groups.append(build_or_group(slot, terms[slot]))
    return " AND ".join(groups)

Notice what this function does not do: it never reads rq.slots directly to build search terms. The ResearchQuestion's slot values ("knowledge workers") are what a human wrote when formalizing the question in Module 1 — a single string, not a set of synonyms. The actual search terms always come from the separately-supplied terms dict, because a real search needs many synonyms per concept, not just the one phrase a human happened to type first.

05Limits / What You Cannot Do Yet

Can't do yet

  • Actually query a database — this produces a string, no network call happens
  • Detect that "work-from-home" needs quoting (no space, so quote_if_phrase() misses it — a real, documented limitation)
  • Automatically generate synonyms — you still supply the SlotTerms yourself

Can do

  • Turn a structured question into one reproducible, auditable search string
  • Show, concretely, how widening which slots you search changes the string (and why that matters)
  • Catch a missing or empty slot before a malformed query goes anywhere

07Brain Exercise

Example 2's query is described as "stricter" and "lower-recall." Why would a reviewer ever deliberately choose the stricter version, if it risks missing relevant studies?
When the broader search returns too many irrelevant records to screen by hand within a realistic timeframe. Sensitivity (recall) and manageable volume are in tension — a rapid review (Module 22) might deliberately trade some recall for a search a single reviewer can actually finish in the time available, as long as that tradeoff is documented rather than hidden. The "right" choice depends on the review's actual constraints, not a universal rule — which is exactly why this module makes the choice explicit and visible rather than baking in one fixed default silently.

08There Are No Dumb Questions

Why doesn't the query builder just read the free-text value already sitting in rq.slots["population"] instead of making me supply a whole separate SlotTerms dict?
Because "knowledge workers" alone would miss every paper that instead said "office employees" or "salaried staff." The whole point of a search strategy is synonym coverage — one phrase per concept is exactly what a comprehensive search can't afford to rely on.
What stops someone from accidentally including a controlled-vocabulary term that doesn't actually exist in the target database?
Nothing in this module — it has no connection to a live database yet, so it can't validate that a MeSH term is real. That check becomes possible starting in Module 4, once there's an actual API to ask.
Could I use this to build an OR-only or NOT-containing query instead of AND-of-ORs?
Not without modifying the code — build_query() always joins slot-groups with AND, by design, because AND-of-ORs is the standard, well-understood shape for a PICO-style search. NOT is deliberately absent everywhere in this module, for the reason covered in Prerequisite 2's warning box: it silently discards relevant studies too easily.

09What's Next

A boolean query string is still just text — nothing has been searched yet, and there's nowhere to put the results even if it had been. Module 3 builds the canonical Record shape that every result, from every source, will eventually get normalized into.
