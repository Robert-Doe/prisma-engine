Module 10 — Track 1: Core EngineData Extraction Form Engine

00Before You Start

No new prerequisite page — this module builds on the general idea of a validated, structured schema you've already seen in Module 1's framework slots and Module 2's controlled vocabulary.

01The Big Analogy

The tax form, not the blank notepad A tax authority doesn't ask you to describe your income in a paragraph — it gives you a form with a specific box for a specific number, and the form rejects "a lot of money" the moment you try to submit it. The box doesn't know your actual income; it only guarantees that whatever you did submit is at least the right shape — a number, not a sentence.

REMOTE_WORK_SCHEMA is that form. It doesn't read a paper and figure out its sample size for you — a human still has to read the paper and type 210. What the schema guarantees is that "about two hundred" gets rejected before it ever reaches a row of your evidence table, the same way the tax form rejects a sentence where it expects a number.

02What Happens, Step by Step

  1. An ExtractionSchema is a list of ExtractionFields, each with a name, an expected Python type, whether it's required, and an optional value validator
  2. A human reads a paper and fills in a plain dict of extracted values — this module never reads the paper for you
  3. validate_extraction() checks every required field is present, every present value matches its declared type, and every value with a validator passes it
  4. The first thing wrong raises ExtractionValidationError with a specific, actionable message — not a generic "invalid data"
  5. Data that survives validation becomes an ExtractedRecord, tied to the Record it was extracted from

04The Code, Explained

def validate_extraction(schema, data):
    for f in schema.fields:
        if f.name not in data:
            if f.required:
                raise ExtractionValidationError(f'missing required field "{f.name}"')
            continue
        value = data[f.name]
        if not isinstance(value, f.field_type):
            raise ExtractionValidationError(
                f'field "{f.name}" expected {f.field_type.__name__}, '
                f'got {type(value).__name__} ({value!r})'
            )
        if f.validator is not None and not f.validator(value):
            raise ExtractionValidationError(f'field "{f.name}" failed validation: {value!r}')

And the reusable validator factory that makes controlled-set checks a one-liner:

def one_of(allowed: set):
    return lambda v: v in allowed

# usage:
ExtractionField("study_design", str, validator=one_of({"RCT", "cohort", "cross-sectional", "qualitative"}))

05Limits / What You Cannot Do Yet

Can't do yet

  • Read a paper and fill in the data itself — that's still a human's job, by design
  • Cross-field validation ("if design is 'qualitative', sample_size should probably be small") — each field is validated independently
  • Assemble many extracted records into a comparable table — that's Module 14

Can do

  • Guarantee every accepted extraction has the right fields, right types, right allowed values
  • Name exactly what's wrong with rejected data, not just that something is
  • Make "what counts as a valid extraction" an explicit, inspectable schema instead of an unwritten convention in someone's head

07Brain Exercise

Why does this schema separate "type check" (`isinstance`) from "value validator" instead of doing both in one function per field?
Because they fail for different reasons and get fixed differently. A type failure means the data wasn't even the right kind of thing (a sentence where a number belonged) — a data-entry mistake. A validator failure means the data was the right kind of thing but the wrong specific value (a real string, just not one of the four allowed study designs) — a classification mistake. Keeping them separate means the error message can be specific about which kind of mistake happened, and means adding a new value constraint later never requires touching the type-checking code at all.

08There Are No Dumb Questions

Isn't it a little disappointing that "Data Extraction Form Engine" doesn't actually extract data from the paper?
It's a real, deliberate boundary, not a shortfall — see DECISIONS.md. Reliably pulling a sample size out of arbitrary prose is genuinely hard NLP, explicitly out of this course's stated scope. What this module proves — that a validated schema makes structured data trustworthy — is real and useful on its own, independent of who or what fills the form in.
Could two different reviewers extracting the same paper get different valid answers?
Yes, easily — the schema only validates shape (is this an int, is this one of four allowed strings), not correctness (did you read the paper's methods section accurately). Real systematic reviews handle this with double extraction — two reviewers independently fill the same form, then reconcile disagreements — which is a human process this module doesn't attempt to automate.
Why is `comparison_group` a free-text `str` field with no `one_of()` validator, unlike `study_design`?
Because a comparison group genuinely varies too much across studies to fit a small fixed set — "in-office workers," "pre-pandemic baseline," "hybrid-schedule workers" are all real, legitimate values a set-based validator would have to either include all of (defeating the purpose of a controlled set) or wrongly reject.
