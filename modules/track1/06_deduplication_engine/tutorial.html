00Before You Start

Finished Module 5 — this module exists specifically to clean up the duplicate risk that module's tutorial admitted and deliberately left unsolved.

01The Big Analogy

DNA test vs. police sketch Two ways to confirm two crime-scene samples came from the same person. A DNA match is definitive — if it matches, that's the same person, full stop, regardless of what they were wearing or how the scene looked different this time. A police sketch comparison is a judgment call — a resemblance score, not a certainty — and a good detective never treats "looks a lot like" as "is," they set a threshold for how confident they need to be, and they write down exactly why they made the call.

normalize_doi() comparison is the DNA test — cheap, unambiguous, run first. title_similarity() is the sketch comparison — probabilistic, run second, always logged with a score. And just like a real detective, this module refuses to arrest a stranger just because they resemble a suspect: two different papers with similar-sounding titles are supposed to walk free.

02What Happens, Step by Step

  1. Pass 1 (DOI): every record's DOI is normalized (lowercase, URL prefix stripped) and grouped — a second record with a normalized DOI already seen is marked a duplicate immediately, with score=1.0
  2. Pass 2 (fuzzy title): among whatever survives Pass 1, every remaining pair is compared with title_similarity() — normalized, punctuation-stripped titles run through difflib.SequenceMatcher
  3. A pair scoring at or above title_threshold (default 0.90) — and, if min_author_overlap is set, sharing enough last names — gets flagged; the later-indexed record is marked a duplicate of the earlier one
  4. Every single removal, from either pass, is recorded as a DuplicateMatch naming which record was kept, which was removed, why ("exact_doi" or "fuzzy_title"), and the exact score — nothing is ever silently dropped

04The Code, Explained

The full two-pass structure, in one place:

def deduplicate(records, title_threshold=0.90, min_author_overlap=0.0):
    removed = [False] * len(records)
    matches = []

    # Pass 1: exact DOI
    doi_to_first_index = {}
    for i, rec in enumerate(records):
        norm = normalize_doi(rec.doi)
        if norm is None:
            continue
        if norm in doi_to_first_index:
            removed[i] = True
            matches.append(DuplicateMatch(doi_to_first_index[norm], i, "exact_doi", 1.0))
        else:
            doi_to_first_index[norm] = i

    # Pass 2: fuzzy title, only among Pass 1's survivors
    survivors = [i for i in range(len(records)) if not removed[i]]
    for a_pos, i in enumerate(survivors):
        for j in survivors[a_pos + 1:]:
            if removed[j]:
                continue
            score = title_similarity(records[i].title, records[j].title)
            if score >= title_threshold:
                removed[j] = True
                matches.append(DuplicateMatch(i, j, "fuzzy_title", score))

Notice Pass 2 only ever compares records still standing after Pass 1 — the cheap, certain pass shrinks what the expensive, uncertain pass has to work over.

05Limits / What You Cannot Do Yet

Can't do yet

  • Scale gracefully — Pass 2 is O(n²); fine for hundreds of records, a real problem at tens of thousands
  • Choose intelligently which duplicate copy to keep (always keeps the earlier index, regardless of which has more complete data)
  • Catch a duplicate whose title was heavily reworded between preprint and published version — similarity would score too low

Can do

  • Catch exact duplicates instantly and unambiguously via DOI, regardless of case or URL formatting
  • Catch near-duplicates fuzzy title matching finds, with a logged, auditable confidence score
  • Correctly leave alone two different papers that merely sound similar

07Brain Exercise

Record [1] (the no-DOI preprint copy) and Record [3] ("Employee Wellbeing") both lack an exact-DOI match to anything else. Why does one get caught by Pass 2 and the other doesn't?
Because Pass 2 doesn't ask "does this record lack a DOI" — it asks "how similar is this record's title to every other surviving record's title." Record [1]'s title scores 1.000 against Record [0] after normalization (the only difference was a colon vs. a dash). Record [3]'s title scores 0.732 against its nearest neighbor — real, measured dissimilarity, not an assumption. The presence or absence of a DOI only determines which pass a record's fate gets decided in, never the fuzzy-matching verdict itself.

08There Are No Dumb Questions

Why is the threshold 0.90 and not something else?
It's a convention, tuned against the specific test cases in this module's demo — high enough that "Employee Wellbeing" (0.732) stays safely below it, low enough that a punctuation-only title variant (1.000) clears it easily. A real review might tune this differently depending on how noisy its sources' titles tend to be; the point is that it's an explicit, visible parameter, not a hidden magic number.
What happens if two completely different papers happen to share the exact same (wrong) DOI due to a data-entry error in the source?
This module would merge them — it trusts DOI equality completely, by design, because DOIs are supposed to be globally unique identifiers. A source-level data error violating that guarantee is a real, if rare, risk this module doesn't defend against; if you suspect it, the DuplicateMatch audit trail is exactly what lets a human reviewer spot-check "kept_index=0, duplicate_index=2, reason=exact_doi" and catch the mistake.
Could this module produce a false negative — miss a real duplicate?
Yes, and the Limits section names one concretely: a paper whose title changed substantially between preprint and final publication would score too low on fuzzy title matching and slip through as two "different" records. No dedup algorithm at this level of sophistication catches everything — which is exactly why every decision this module makes is logged instead of hidden, so a human reviewer doing a final pass has a real audit trail to work from.
