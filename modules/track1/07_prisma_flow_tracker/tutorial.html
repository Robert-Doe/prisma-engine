01The Big Analogy

Double-entry bookkeeping A bookkeeper doesn't just write down numbers — every entry has to balance against another entry, and at the end of the period, the books either balance or they don't. If they don't, that's not a footnote, it's a stop-everything signal that money went somewhere unaccounted for. Nobody trusts a ledger that never checks its own arithmetic.

PrismaFlowTracker is that ledger, and validate_conservation() is the balance check. Every record that enters a stage has to come out the other side as either "included" or "excluded, for this specific named reason" — never just vanish. If the numbers don't add up, FlowConservationError is the accounting equivalent of the books not balancing.

02What Happens, Step by Step

  1. log_identification(source, count) records how many records came from each source — called once per source, e.g. once for PubMed, once for arXiv
  2. log_deduplication(removed_count) records how many were removed as duplicates
  3. log_screening(excluded_by_reason, included_count) records the title/abstract screening outcome — a dict of exclusion reasons to counts, plus how many passed
  4. log_eligibility(...) records the same shape for the full-text stage
  5. validate_conservation() checks, stage by stage, that inputs equal outputs — raising FlowConservationError naming the exact stage and the exact mismatch if they don't

04The Code, Explained

The check that does all the actual work:

def validate_conservation(self) -> None:
    if self.screening_included is not None:
        expected = self.after_dedup()
        actual = self.screening_included + self.total_screening_excluded()
        if actual != expected:
            raise FlowConservationError(
                f"screening stage: {expected} entered but {actual} accounted for "
                f"({self.screening_included} included + {self.total_screening_excluded()} excluded)"
            )

Notice this isn't checking that the numbers look reasonable — it's checking that they're arithmetically consistent with the stage before them. A tracker that never ran this check could have any numbers typed into it, correct or not, and would never know the difference.

05Limits / What You Cannot Do Yet

Can't do yet

  • Render an actual PRISMA flow diagram image — that's Module 12
  • Track individual records' fates by ID, only aggregate counts per stage
  • Validate that a reason string is a "real" PRISMA-approved exclusion category — any string is accepted

Can do

  • Prove, arithmetically, that no record disappeared unaccounted for between stages
  • Catch a real logging mistake immediately, with the exact stage and mismatch named
  • Produce a complete, real PRISMA-shaped count summary from actual (not simulated) upstream module output

07Brain Exercise

Why does validate_conservation() check the eligibility stage against screening_included, not against after_dedup()?
Because the eligibility (full-text) stage only ever looks at records that already survived screening — that's literally what "passed screening" means. Checking eligibility's total against after_dedup() instead would silently ignore everything screening removed, and a real mismatch at the eligibility stage could hide behind an unrelated, already-explained gap from an earlier stage. Each stage's conservation check has to anchor to the specific count that stage actually received as input.

08There Are No Dumb Questions

What stops someone from just logging fake numbers that happen to balance?
Nothing in this module — conservation checking proves internal consistency, not truthfulness. A tracker fed deliberately fabricated but self-consistent numbers would pass every check here. That's a real, honest limit: this module catches bookkeeping errors, not fraud. Trustworthiness of the underlying counts still depends on the modules that actually produced them being run for real, which is exactly why this demo reuses Modules 4-6's live output instead of hand-typing numbers.
Why is screening simulated here instead of skipped entirely until Module 8 exists?
Because this module's whole job is to prove the tracking and validation mechanism works across a full multi-stage flow — identification through eligibility — not just a two-stage toy case. Simulating the not-yet-built stages, clearly labeled as simulated, lets the demo exercise the complete conservation-checking logic honestly.
Could two different reasons for the same stage get accidentally merged?
No — screening_excluded is a dict keyed by the exact reason string, so "wrong population" and "Wrong Population" would be tracked as two separate reasons (case-sensitive). That's a real, minor gotcha worth knowing about if you're logging reasons from multiple places in a larger pipeline.
