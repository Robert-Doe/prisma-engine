01The Big Analogy

The airport security line ID check, bag scan, metal detector, in that fixed order. If your ID doesn't match your boarding pass, you get pulled aside for that reason — nobody also blames you for what the metal detector might have found, because you never got that far. One line, one order, and whichever checkpoint stops you first is the only reason recorded.

screen() runs the exact same way: DEFAULT_RULES is the fixed line of checkpoints, and the first one a record fails is the only reason logged for it — later checkpoints never even see that record.

02What Happens, Step by Step

  1. For each record, screen() walks DEFAULT_RULES in order: has_abstract, then published_2015_or_later, then mentions_relevance_keyword
  2. The first rule whose predicate returns False becomes that record's logged exclusion reason — checked no further
  3. A record that passes every rule goes into result.included
  4. result.excluded_by_reason() tallies exclusions into exactly the dict[str, int] shape Module 7's log_screening() expects — no conversion step needed

04The Code, Explained

def screen(records, rules):
    result = ScreeningResult()
    for rec in records:
        failed_reason = None
        for rule in rules:
            if not rule.predicate(rec):
                failed_reason = rule.name
                break                     # <- later rules never run
        if failed_reason is not None:
            result.excluded.append((rec, failed_reason))
        else:
            result.included.append(rec)
    return result

And the rule that turned out to matter most in the real run — not a hypothetical, an actual observed outcome:

def has_abstract(rec: Record) -> bool:
    return bool(rec.abstract and rec.abstract.strip())

05Limits / What You Cannot Do Yet

Can't do yet

  • Screen on population/design criteria that need full text, not just title/abstract — that's Module 9
  • Recover from an upstream data gap — a record with no abstract is always excluded by this rule set, correctly but unavoidably
  • Weigh partial matches — a rule is strictly pass/fail, no "probably relevant" middle ground

Can do

  • Apply the identical criteria to every record, with zero human inconsistency between the first record screened and the thousandth
  • Log a specific, correct reason for every exclusion
  • Feed directly into Module 7's PRISMA tracker with no glue code

07Brain Exercise

Why does has_abstract run first in DEFAULT_RULES, before the relevance-keyword check, rather than after it?
Because mentions_relevance_keyword searches title and abstract text for a stem. If it ran first on a record with no abstract, it would still technically "work" (searching an empty string just fails to find the keyword) — but the record would then be excluded for "no productivity/performance/output keyword found," which is a misleading, secondary consequence of the real problem. Ordering has_abstract first ensures the reported reason is always the most upstream, most accurate one: you can't meaningfully evaluate relevance on text that was never there.

08There Are No Dumb Questions

Isn't excluding every abstract-less record a huge loss of potentially relevant studies?
In a real review, yes — which is exactly why a real review wouldn't stop at esummary. This module's honest reporting of "5 excluded for missing abstracts" is the signal that should send a reviewer back to fix the upstream extraction (fetch full abstracts via efetch, or retrieve them from another source) rather than accept the loss silently.
Could I write a rule that checks something Module 3's Record doesn't currently store, like language?
Not directly — a rule's predicate can only inspect fields that actually exist on the Record. Adding a language criterion for real would mean first extending Module 3's Record model (and whichever parser can supply it) with a language field, then writing the rule against it.
What happens if rules is an empty list?
Every record passes — the inner loop never finds a failing rule, so failed_reason stays None and everything goes to result.included. That's a real, sensible edge case, not a special-cased behavior: "no criteria" correctly means "nothing gets excluded."

09What's Next

Title/abstract screening is a coarse first pass — real eligibility decisions often need the full text, not just what's visible from an abstract. Module 9 builds the second-pass full-text eligibility engine, operating only on the records that survived this stage.
