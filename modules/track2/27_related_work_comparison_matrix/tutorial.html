01The Big Analogy

The spec-sheet comparison table A tech review site doesn't describe three competing phones in three separate paragraphs — it builds one table: battery life, camera resolution, price, weight, one row per phone, one column per spec. You can read straight down the "battery life" column and immediately see which phone wins that dimension, without re-reading any review.

That's what a USENIX-style Related Work section's comparison table does with prior systems instead of phones. COMPARISON_SCHEMA is the spec sheet's column list — approach type, which attacks it targets, whether it's ML-based. build_evidence_table() (reused unchanged from Module 14) is what turns seven real, live-fetched papers into that one readable table.

02What Happens, Step by Step

  1. Module 5's fetch_arxiv() runs a real, live search for Spectre/Meltdown-class side-channel papers
  2. Module 13's backward_snowball() pulls in real related work from a real, resolved DOI's own reference list
  3. Module 6's deduplicate() merges both sources into one unique set of real papers
  4. extract_dimensions() classifies each paper's approach using only its own real title/abstract text — never an assumed fact about what the paper "probably" does
  5. Module 10's extract() and Module 14's build_evidence_table(), reused unchanged, assemble the final comparison matrix

04The Code, Explained

def classify_approach(text: str) -> str:
    lowered = text.lower()
    if any(k in lowered for k in ("detect", "identification of")):
        return "detection"
    if any(k in lowered for k in ("prevent", "mitigat", "defense", "banish", "protect")):
        return "mitigation"
    if any(k in lowered for k in ("discover", "automated discovery", "survey")):
        return "discovery/analysis"
    return "unspecified"

Every branch is grounded in the paper's own words. When there are no words to search — a paper with no abstract on file — the function correctly falls through to "unspecified" rather than guessing.

05Limits / What You Cannot Do Yet

Can't do yet

  • Extract real technical detail (performance overhead percentages, exact hardware tested) — only what a title/abstract's own words support
  • Classify a paper accurately if its abstract is missing (correctly falls back to "unspecified," but that's a real information loss)
  • Generate the actual novelty/gap argument — that's Module 28

Can do

  • Build a real, USENIX-style comparison matrix from genuinely live, multi-source data
  • Keep every classification traceable and auditable against the paper's own real text
  • Report a real data gap (missing Crossref abstracts) honestly instead of inventing a classification to fill it

07Brain Exercise

BranchScope and KASLR is Dead both classified as "unspecified" — but they're both real, well-known, on-topic papers with clear technical contributions. Is this module's output misleading?
Only if read without its own stated limits — which is exactly why this module reports the gap explicitly instead of hiding it. The alternative would be worse: guessing "mitigation" or "detection" for these two papers based on their titles alone sounding vaguely technical, or based on outside knowledge this exercise can't verify against the papers' own text, would be exactly the kind of fabricated-sounding-real claim this course's quality bar prohibits. An honest "we don't have enough text to classify this" is more useful to a real researcher than a confident-sounding guess, because it tells them exactly which papers in the matrix need a closer, manual read.

08There Are No Dumb Questions

Why does this module use a different seed DOI than Module 13's own original demo?
Module 13's seed was a fuzz-testing paper — completely unrelated to Spectre/Meltdown. Snowballing from it here would have pulled in off-topic related work into a supposedly on-topic comparison matrix. Finding a real, on-topic, verified seed DOI (SafeSpec, confirmed live against Crossref before use) keeps the whole matrix coherent.
Could this module accidentally classify a paper wrong even when an abstract IS available?
Yes — a paper about "preventing false positives in Spectre detection tools" would trigger both "detect" and "prevent" markers, and `classify_approach()`'s `if/elif`-style ordering would call it "detection" (checked first) even though "prevention of false positives" isn't really about attack mitigation. Keyword heuristics have real, describable failure modes like this one, the same honesty this course has applied to every other heuristic since Module 1.
Is 7 papers enough for a real USENIX-style related work section?
For a worked example, yes; for a real paper, usually not — a genuine related-work section for an active research area like this would typically survey dozens of papers. This module demonstrates the mechanism at a scale a reader can actually verify by hand, not a claim that 7 papers constitutes adequate coverage of the field.
