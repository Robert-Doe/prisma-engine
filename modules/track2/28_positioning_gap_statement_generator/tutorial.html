01The Big Analogy

The patent examiner's prior-art search A patent examiner doesn't reject a new invention just because parts of it resemble existing patents — plenty of inventions combine known ideas in a new way. What actually blocks a patent is a single prior patent (or a combination the examiner can construct) that already covers every claim at once. An examiner who found "patent A covers claims 1 and 2, but not 3" hasn't found prior art that blocks the application — they've found a near-miss worth citing in the application's own "related work" discussion, to show the inventors knew about it and are still claiming something new.

find_satisfying_papers() is the examiner's search for a single prior work that blocks the whole claim. find_near_misses() is the examiner's list of "close, but not quite" prior art, each with the specific claim it doesn't cover.

02What Happens, Step by Step

  1. A GapCriteria states every dimension a hypothetical new contribution would need — e.g. detection + targets Spectre + targets Meltdown + non-ML
  2. find_satisfying_papers() checks the real comparison matrix for any paper matching ALL required dimensions at once — the full conjunction, not a majority
  3. If one exists, that's not a gap — the function says so directly, naming the paper
  4. If none exists, find_near_misses() finds every paper satisfying SOME dimensions, and reports exactly which ones it's missing
  5. verify_claim_grounded() re-derives each near-miss's claimed-missing dimension directly from that paper's real title/abstract text, right now — not trusted from the table alone

04The Code, Explained

def find_satisfying_papers(table, criteria):
    return [
        row for row in table.to_dict_rows()
        if all(row.get(k) == v for k, v in criteria.required_dimensions.items())
    ]

That all(...) is the entire logical core of a real novelty claim — every required dimension, together, in one paper. Change it to any(...) and the module would be answering a much weaker, much less useful question.

05Limits / What You Cannot Do Yet

Can't do yet

  • Write the actual prose paragraph a paper's Related Work section would contain — only the structured claim and its grounding
  • Detect negated claims correctly — "without machine learning" and "using machine learning" both match the same substring check (see DECISIONS.md for a real bug this caused during development)
  • Judge whether a discovered gap is actually worth publishing about — it only checks combinatorial coverage, not significance

Can do

  • Mechanically and correctly determine whether a specific combination of dimensions is covered by existing real work
  • Name exactly which dimension each close prior work is missing, not just that it's "different"
  • Re-verify a grounding claim against a paper's actual text at the moment it's cited, not just trust an earlier extraction

07Brain Exercise

This module's own development hit the exact same negation-blindness bug Module 24 already documented — in a totally different function, for a totally different purpose. What does that recurrence actually tell you?
That the weakness isn't a quirk of Module 24's specific negation word list — it's a structural property of any heuristic that decides meaning by checking whether a substring is present, without considering what surrounds it. Any new module in this course (or beyond it) that classifies text by keyword presence alone inherits this same risk, whether or not its author has ever read Module 24's tutorial. Recognizing "this is the same class of problem as before," rather than treating each occurrence as a one-off surprise, is what lets you anticipate it in the next heuristic you write instead of discovering it the hard way again.

08There Are No Dumb Questions

Why does the module cite ALL 7 papers as near-misses instead of just the closest one or two?
Because a real Related Work section is expected to demonstrate awareness of the field, not just the single most similar paper — omitting a relevant near-miss risks a reviewer pointing out "you didn't cite X," a real, common rejection reason at venues like USENIX. Showing every near-miss, each with its specific gap, is the safer and more honest default.
What would happen if `GapCriteria` required a dimension that doesn't exist in the schema, like `"performance_overhead"`?
`row.get(k)` would return `None` for every row (the key never exists in any row's dict), so `None == v` would be `False` for any real required value — every paper would be reported as "missing" that dimension, which happens to be the technically correct (if uninformative) answer, rather than a crash.
Is `verify_claim_grounded()` actually catching the negation-blindness bug it's meant to guard against?
No — and that's worth being honest about, per DECISIONS.md. It re-runs the exact same `extract_dimensions()` function, so a systematic error in that function (like the negation-substring issue) would reproduce identically on re-check, not get caught. What it does catch is drift — a table value that's stale or was corrupted after extraction — a real but narrower guarantee than "this claim is semantically correct."
