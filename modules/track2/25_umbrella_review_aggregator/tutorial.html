Module 25 — Track 2: Applied LayerUmbrella Review Aggregator

Depends on Track 1: Module 11 Module 14

00Before You Start

Read Module 0's Umbrella Review concept page — this module's central hazard (overlapping primary studies) is exactly what that page's warning box describes.

01The Big Analogy

The shared guest at three parties Three hosts each report their party's guest list: 4, 4, and 2 people. Add those up and you'd report 10 people attended something this weekend. But if the same two people went to both the first and second party, the real number of distinct people who attended anything is 8, not 10 — two guests got counted twice just because they showed up twice.

total_unique_primary_studies() is the version of this module that actually checks guest lists against each other instead of just adding up party sizes. Run on this module's own demo data, the naive sum is 10 and the real, deduplicated total is 8 — the exact same shared-guest problem, with real primary studies instead of party guests.

02What Happens, Step by Step

  1. Each IncludedReview carries a title and the set of primary-study DOIs it included — the review, not a primary study, is this module's unit of analysis
  2. AMSTAR_LITE_CHECKLIST — built from Module 11's exact Checklist/ChecklistItem classes — appraises each review's own conduct (protocol registration, search comprehensiveness, duplicate screening) via Module 11's unmodified score_checklist()
  3. total_unique_primary_studies() computes the real, deduplicated evidence base via set union — not a sum of each review's count
  4. compute_overlap() reports, for every pair of included reviews, exactly how many primary studies they share and what fraction of their combined evidence that overlap represents

03A Map of the State

Review A: {s1, s2, s3, s4}     appraisal: 0.90 -> "low risk"
Review B: {s3, s4, s5, s6}     appraisal: 0.40 -> "high risk"
Review C: {s7, s8}             appraisal: 0.90 -> "low risk"
        │
        ▼  naive_total = len(A) + len(B) + len(C) = 4 + 4 + 2 = 10
        │
        ▼  total_unique_primary_studies() = |A ∪ B ∪ C|
           = {s1,s2,s3,s4,s5,s6,s7,s8} = 8
        │
        ▼  gap = 10 - 8 = 2   <- s3 and s4, double-counted (in both A and B)
        │
        ▼  compute_overlap()
A <-> B: shared={s3,s4}, count=2, union={s1..s6}=6, pct=33.3%
A <-> C: shared={}, count=0, pct=0.0%
B <-> C: shared={}, count=0, pct=0.0%

04The Code, Explained

def total_unique_primary_studies(reviews: list[IncludedReview]) -> int:
    all_dois: set[str] = set()
    for r in reviews:
        all_dois |= r.primary_study_dois     # set union — this IS the dedup
    return len(all_dois)

One line does the entire job. The bug this module exists to prevent isn't complicated to fix — it's easy to forget, if you're used to just summing counts from a list of reports.

05Limits / What You Cannot Do Yet

Can't do yet

  • Match the real AMSTAR-2 instrument, which has 16 detailed items — this is a simplified, honestly-labeled subset
  • Compute the more sophisticated "corrected covered area" overlap metric real umbrella-review methodology sometimes uses — only raw set overlap
  • Resolve a conflicting appraisal (if two overlapping reviews reached different conclusions about a shared primary study) — overlap is detected, not reconciled

Can do

  • Appraise reviews with the exact same real machinery Track 1 built for primary studies
  • Catch and quantify a real, common umbrella-review hazard — double-counted primary-study evidence — with an exact number, not a vague warning
  • Pinpoint precisely which pair of included reviews caused the overlap

07Brain Exercise

Review B was appraised as "high risk" (no registered protocol, no duplicate screening). Should its primary studies be trusted the same as Review A's, given they overlap on 2 studies?
This is exactly the kind of question this module surfaces but deliberately doesn't answer for you — see the Limits section. Studies s3 and s4 are included in both a "low risk" review (A) and a "high risk" review (B); this module reports that overlap and both appraisals honestly, but reconciling what to conclude when two reviews of differing quality both included the same evidence is a real, human editorial judgment call, not a mechanical one. What this module guarantees is that you'd actually see this tension — compute_overlap() makes it visible — rather than it disappearing inside a single combined count.

08There Are No Dumb Questions

Why does this module reuse Module 11's checklist classes instead of Module 22's, since Module 22 also built a "reduced" checklist?
Because Module 22's reduction (fewer items, same subject — primary studies) and this module's adaptation (a different subject entirely — reviews) are different kinds of change. Both trace back to the same root classes in Module 11, which is the actual point: one set of classes supports both a "fewer items" adaptation and a "different unit of analysis" adaptation without modification.
What would happen with real DOIs that have formatting inconsistencies, like Module 4 found with "Telework" vs "Teleworking"?
This module's overlap detection depends on exact string matches between DOI sets — it doesn't call Module 6's `normalize_doi()`. Two representations of the same DOI (different case, a URL prefix) would be treated as different studies, silently under-counting real overlap. That's a real, un-addressed gap; a production version of this module should normalize DOIs the same way Module 6 and Module 23 already do.
Is 33.3% overlap between two reviews a lot?
There's no universal threshold — real umbrella-review guidance treats substantial overlap as a signal to investigate and report transparently, not an automatic disqualifier. What matters is that the number is visible at all, so an editor or reader can make that judgment themselves instead of it being invisible inside a combined total.
