01The Big Analogy

The neighborhood scout, not the building inspector Module 0 described a scoping review as a scout on a motorbike — this module is where that scout actually gets to work. A neighborhood scout doesn't go inside every building and check its wiring, plumbing, and foundation for safety — that's a building inspector's job, one building at a time, in depth. The scout's job is riding every street and coming back with a map: how many houses, how many shops, how many apartment blocks, roughly where they cluster.

This module never calls Module 11's risk-of-bias scorer — not because it forgot to, but because a scout doesn't inspect foundations. Its actual output, summarize_breadth(), is a map of what exists, not a verdict on whether any single building is safe.

02What Happens, Step by Step

  1. A PCCQuestion (Population, Concept, Context — the real JBI framework for scoping reviews) replaces Module 1's PICO, validated the same way but as its own parallel class
  2. build_widened_query() reuses Module 2's build_or_group() directly, but includes every slot instead of Module 2's narrowed default — breadth, not sensitivity-within-volume
  3. Screening reuses Module 8's screen()/ScreeningRule unchanged, with only a relevance rule — no design or date filtering
  4. A charting form (CHARTING_SCHEMA) reuses Module 10's exact ExtractionField/ExtractionSchema classes, with fields describing study characteristics instead of quantitative findings
  5. summarize_breadth() — new code — tallies charted records by category into a breadth map, the review's actual deliverable

04The Code, Explained

def build_widened_query(terms: dict[str, SlotTerms]) -> str:
    # Unlike Module 2's DEFAULT_SEARCH_SLOTS, which deliberately excludes
    # some slots — a scoping review wants maximum breadth instead.
    groups = [build_or_group(slot, slot_terms) for slot, slot_terms in terms.items()]
    return " AND ".join(groups)

Compare this to Module 2's build_query(), which filters terms down to DEFAULT_SEARCH_SLOTS before building groups. This function skips that filter entirely — same building block, opposite default.

05Limits / What You Cannot Do Yet

Can't do yet

  • Judge whether any charted study is trustworthy — that's explicitly out of scope for this review type
  • Pool anything numerically — a breadth map is categorical, not a quantitative synthesis
  • Reuse Module 1's Framework enum directly for PCC — Python enums can't be extended after the fact

Can do

  • Answer "what does this field look like" with a real, structured map instead of a narrative guess
  • Reuse Track 1's real query-building, screening, and extraction machinery for a genuinely different purpose
  • Prove Track 1's building blocks compose into more than just the one pipeline they were originally built for

07Brain Exercise

Module 1's Q&A explicitly said "want to add a new framework? Add an entry to FRAMEWORK_SLOTS." Why didn't this module just do that for PCC?
Because that answer was true for adding a new entry to a dict (`FRAMEWORK_SLOTS`) — genuinely easy — but PCC also needed a new value in the `Framework` enum itself for the rest of Module 1's code (like `suggest_framework_verbose()`'s return type) to reference it consistently, and Python doesn't support adding members to an `Enum` after its class body has executed. This is a real, discovered gap between "the dict is extensible" and "the whole framework concept is extensible" — which is exactly why this module builds a parallel `PCCQuestion` class instead of forcing a fit that Python's own type system doesn't actually allow.

08There Are No Dumb Questions

If PCC and PICO are structurally so similar (both are validated slot dictionaries), why not just make one generic "SlottedQuestion" base class both inherit from?
That would be a reasonable refactor in a real codebase — but it would mean modifying Module 1, which this course's Track 2 modules deliberately avoid doing, to keep every already-built, already-verified Track 1 module stable for anyone relying on it exactly as documented. Track 2 proves Track 1's pieces are reusable as they are, not that they're infinitely refactorable.
Why does the charting form require `topic_focus` but make `geographic_region` optional?
Because a real charting form's job is answering the review's specific breadth question, and this scoping review's PCC context is about organizational settings and topic areas — geography is useful context, not central to the question, similar to how Module 10's `outcome_measure` field is optional because not every source reliably reports it.
Could `summarize_breadth()` be reused by other Track 2 modules?
Yes, structurally — anything that builds an evidence-table-shaped object with categorical fields could reuse it as-is. Module 22 (Rapid Review Adapter) or a future bibliometric module could import it directly rather than reinventing category tallying.
