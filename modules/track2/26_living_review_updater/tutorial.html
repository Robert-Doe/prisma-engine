00Before You Start

Read Module 0's Living Systematic Review concept page — this module implements the version-tracked, incrementally-updated lifecycle it describes.

01The Big Analogy

A motion-detecting security camera, not a nightly re-record One camera re-records an entire empty room from scratch every night, then someone has to rewatch all of it to find the ten seconds that mattered. A better camera remembers what it already saw, and only flags genuinely new motion since the last check.

run_update() is the second kind of camera. seen_dois, persisted to a real JSON file between runs, is its memory. Every update fetches live results, but only the ones seen_dois doesn't already recognize ever reach dedup and screening — the rest are correctly skipped, not reprocessed.

02What Happens, Step by Step

  1. load_state() reads the previous update's LivingReviewState from disk — version number, timestamp, every DOI seen so far, cumulative included count
  2. Module 5's search_pubmed() fetches fresh, live results
  3. Each fetched record is checked against seen_dois (normalized via Module 6's normalize_doi()) — only genuinely new ones proceed
  4. Only the new records go through Module 6's deduplicate() and Module 8's screen() — not the whole historical corpus
  5. save_state() writes an incremented version, updated seen_dois, and an updated cumulative included count back to disk

03A Map of the State

Update #1 (state.json doesn't exist yet)
  load_state() -> LivingReviewState(version=0, seen_dois=[])
  search_pubmed(query) -> 5 live records
  none in seen_dois -> all 5 are "new"
  dedup + screen the 5 new records
  save_state(version=1, seen_dois=[5 DOIs], ...)

Update #2 (run moments later)
  load_state() -> LivingReviewState(version=1, seen_dois=[5 DOIs from #1])
  search_pubmed(query) -> the SAME 5 live records (nothing changed in seconds)
  all 5 already in seen_dois -> 0 are "new"
  dedup + screen an EMPTY list — correctly nothing to process
  save_state(version=2, seen_dois=[still the same 5 DOIs], ...)

04The Code, Explained — including the real mistake

The first version of this line logged the wrong count:

# WRONG (first draft) — logged the full fetch, not just what was actually processed:
tracker.log_identification("PubMed (this update only)", len(records))

# Running update #2 with this line raised a REAL FlowConservationError:
#   "screening stage: 5 entered but 0 accounted for (0 included + 0 excluded)"
# because 5 records were logged as "identified," but 0 of them ever
# reached dedup/screening — they were all correctly filtered out as
# already-seen BEFORE the tracker's stages even started.

The fix is one word different, but it's the difference between correct and incorrect bookkeeping:

# CORRECT: only the records that actually enter this update's pipeline
tracker.log_identification("New since last update", len(new_records))

05Limits / What You Cannot Do Yet

Can't do yet

  • Track identity for records with no DOI — they're reprocessed every update, always, reported explicitly via records_without_doi_always_reprocessed
  • Re-evaluate a previously-included record if screening criteria change between versions — old inclusions are never revisited
  • Run on a schedule by itself — run_update() is one manual call, not a cron job

Can do

  • Persist real state between separate process runs and correctly diff against it
  • Process only genuinely new records, not the full historical corpus, on every update
  • Prove incrementality with two real, live, moments-apart update cycles — not simulated ones

07Brain Exercise

Why did the original bug only show up on update #2, and never on update #1?
Because on update #1, every fetched record genuinely was new — new_records and records were the exact same list, by coincidence, since the state was empty. Logging len(records) instead of len(new_records) happened to produce the right number anyway, purely because there was nothing yet to filter out. The bug was latent from the first line of code — it just had no way to become visible until a second update actually filtered something out. This is a very common shape of real bug: correct-looking on the first run, wrong the moment the code's actual assumption (that fetched and new mean the same thing) stops holding.

08There Are No Dumb Questions

What happens if PubMed's index somehow returns fewer results on a later update than an earlier one (a record gets retracted or removed)?
This module's `seen_dois` only ever grows — nothing removes a DOI once it's been seen. A retracted record would simply never be flagged as new again; this module doesn't detect or handle retractions, a real gap worth knowing about for anything actually deployed long-term.
Why does `UpdateReport` report `records_without_doi_always_reprocessed` instead of just silently reprocessing them?
Because silently reprocessing them would hide a real accuracy gap — someone reading only the "new" count would have no way to know some of those "new" records might actually be repeats the system simply couldn't recognize. Naming the count directly is the same honesty principle as every other module's explicit Limits section, just expressed as a return value instead of prose.
Could this module's incremental pattern be reused for something other than a living review?
Yes — anywhere a pipeline needs to process "what's changed since last time" instead of everything from scratch. Module 23's citation graph, run periodically, could use the identical state-diffing pattern to track newly-appearing citations without re-fetching the whole graph each time.
