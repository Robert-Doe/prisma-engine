00Before You Start

Read Module 0's Rapid Review concept page — this module implements exactly the three simplifications it names.

01The Big Analogy

The two-hour deadline, not the six-week investigation A journalist on a two-hour deadline still checks facts and still names sources — they just can't call every source a six-week investigative piece would. What separates honest deadline journalism from bad journalism isn't the shorter timeline itself; it's whether the published piece says "I confirmed this with two sources but didn't reach a third" or just quietly presents the same confidence a fully verified piece would.

RapidReviewLog is that disclosure. This module doesn't hide that it searched one database instead of two, screened with one reviewer instead of two, and appraised two risk-of-bias domains instead of five — every one of those is printed, with the standard practice it replaces and why, before any result is reported.

02What Happens, Step by Step

  1. run_rapid_review() logs the Identification simplification, then calls Module 4/5's search_pubmed() — PubMed only, fetch_arxiv() never called
  2. It logs the Screening simplification, then calls Module 8's screen() exactly once — no second reviewer, no reconciliation step
  3. It logs the Quality Appraisal simplification, describing REDUCED_RCT_CHECKLIST — built from two of Module 11's own five real ChecklistItems, not five new ones
  4. RapidReviewLog.render() produces the actual disclosure text — standard practice, what this review did instead, and why — for every stage

04The Code, Explained

REDUCED_RCT_CHECKLIST = Checklist("RCT (rapid, reduced)", [
    ChecklistItem("random_sequence", "Was the allocation sequence adequately randomized?"),
    ChecklistItem("blinding", "Were participants/outcome assessors blinded to group assignment?"),
])

Compare this directly to Module 11's RCT_CHECKLIST, which has five items. This is two of the same five — not two similar-sounding new ones — so the relationship between "full" and "reduced" is exact, not approximate.

05Limits / What You Cannot Do Yet

Can't do yet

  • Simulate a real second reviewer — "single-reviewer" here just means screen() runs once; a genuine dual-review workflow needs two actual people
  • Recover the coverage lost by searching one source instead of two — that loss is real, not just logged
  • Retroactively appraise the three dropped risk-of-bias domains from the reduced checklist's output alone

Can do

  • Run a genuinely faster review using real Track 1 code, with every corner cut named and justified
  • Prove the reduced checklist really is a subset of the full one, not a separately-invented approximation
  • Make it impossible for a reader of this review's output to mistake it for a full systematic review

07Brain Exercise

The demo's 0-included result is the same real limitation Module 8 hit. Why does that repetition matter, instead of being an annoying coincidence?
Because it's direct proof this module actually reuses Module 8's real code rather than a simplified reimplementation of it. If this module had its own separate, lighter-weight screening logic, there would be no reason for Module 4's abstract-availability gap to resurface here at all. The fact that it does — unprompted, as a genuine consequence of calling the real screen() and real DEFAULT_RULES — is exactly the kind of evidence this course treats as more trustworthy than a description of intended behavior.

08There Are No Dumb Questions

Why not just skip the risk-of-bias appraisal entirely, the way Module 21's scoping review does?
Because they're compressing for different reasons. Module 21 skips appraisal because a scoping review's goal genuinely doesn't call for it — full stop, regardless of time available. A rapid review still wants to know something about study quality; it just can't afford the full checklist under its time constraint. Reduced appraisal, not omitted appraisal, is the honest reflection of that different motivation.
Could `RapidReviewLog` be reused for a different kind of time-boxed adaptation, not just this specific set of three simplifications?
Yes — `add()` takes any stage name, standard practice, rapid practice, and rationale as plain strings, with no dependency on which specific simplifications this module happens to make. A different rapid-review configuration (say, skipping full-text eligibility entirely) could log that decision through the exact same class.
Is a rapid review with these three simplifications still trustworthy?
Trustworthy for what it honestly claims to be — a faster, lower-coverage, lower-certainty review, disclosed as such. It would not be trustworthy if presented as equivalent to a full systematic review, which is precisely the misrepresentation `RapidReviewLog` exists to prevent.
