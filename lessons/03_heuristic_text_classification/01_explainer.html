Concept Cluster 03Heuristic Text Classification & Its Limits

This is the single most-repeated pattern in the entire course: decide something about a piece of text by checking whether it contains certain words. It appears in at least eight modules across both tracks — and the same specific failure mode (negation-blindness) was independently discovered twice, in two different modules, by two different functions that had never seen each other's code.

01The Big Analogy

A hiring manager who only scans for keywords A resume-screening tool that rejects any resume not containing the word "Python" will reject a genuinely qualified candidate who wrote "I primarily used Python" as "primarily Python-based development" — a real synonym, missed. It will also happily pass a resume that says "I have no experience with Python whatsoever" — the keyword is present, the actual meaning is the opposite of what the check assumes. Every keyword-heuristic function in this course is that hiring manager: fast, transparent, auditable, and blind to exactly this kind of context.

03Why the Same Bug Twice Is the Interesting Part

Module 24's _is_negated():                 Module 27's classify_approach():
  checks for "n't", "not ", "never", etc.     checks for substring "machine learning"
  -> misclassifies "I don't talk to           -> misclassifies "without machine
     anyone" (agreement) as refutational         learning" as ml_based=True

  Two DIFFERENT functions. Two DIFFERENT modules, built weeks apart in
  this course's own construction. Two DIFFERENT specific trigger phrases.
  ONE underlying cause: neither function looks at what surrounds the
  matched word, only whether it's present at all.

That recurrence is itself the finding. It means this isn't a quirk of Module 24's specific negation-word list that a better word list would fix — it's a structural property of substring-presence checking as a technique, visible only once you compare multiple independent instances of it side by side.

04Why This Lives Here, Not Inside One Module

Module 24's own DECISIONS.md and Module 28's own DECISIONS.md each document their own instance honestly — but neither module, read alone, can make the claim this cluster page makes: that this is a recurring class of failure across the whole course, not a one-off. That claim only becomes visible by reading multiple modules' heuristics side by side, which is exactly what a module-scoped tutorial isn't built to do.
